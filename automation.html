Automatic emulation architecture

emuStudio loads a virtual computer, optionally compiles a source file, and runs its CPU without the main window. The host controls execution and shutdown. A usable run also depends on agreements about how plugins wire themselves together, load runnable code, and handle input, output, and interruption.

A compiler can produce a file without loading the CPU's memory. A timed run can exceed its observation limit during shutdown. In both cases, the CLI can return success.

Architecture

The CLI, controller, and plugin JARs share one JVM. emuLib supplies the Java interfaces used across that boundary. TOML describes the machine assembled inside the process. C4 diagram levels · VirtualComputer

Run sequence

  1. Select and load. automation (alias auto) selects the TOML by name, file, or index. GUI mode can ask the operator to choose. Headless mode requires explicit selection. The command supplies EMUSTUDIO_AUTO and EMUSTUDIO_NO_GUI as separate flags. The loader constructs all plugins, initializes compiler → memory → CPU → devices, then resets compiler → memory → devices → CPU.
  2. Prepare the program. If both source and compiler are present, the controller runs compilation and then resets only the CPU. Otherwise, for a machine with a CPU, the same controller operation skips compilation and resets only the CPU. -p supplies an explicit CPU reset address. Without it, the host calls cpu.reset(), which AbstractCPU implements by reading ApplicationApi.getProgramLocation(). The host initializes this location to zero.
  3. Start and observe. In GUI mode, automation calls showGUI(null) on devices that report GUI support. The controller starts CPU.execute() on its machine worker. The caller waits on runCompletion() until the CPU returns or the optional --waitmax elapses. With the flag omitted, it waits indefinitely. The GUI progress window's Stop button sends a stop request to the same controller.
  4. Report and close. Automation logs the observed state and instruction location. The command closes the virtual computer, which waits for the controller to finish before closing the debugger session, destroying devices in reverse order, destroying CPU → memory → compiler, and releasing the class loader and configuration.

Communication model and enforced contracts

Host calls and replies. The loader checks the plugin role and constructor (long, ApplicationApi, PluginSettings). It injects the instance ID, services, and settings. The controller's command executor serializes lifecycle transitions. A separate worker performs reset, compilation, and CPU execution. Completion futures carry the observed RunState or an exception back to the caller. The controller also publishes state to its execution listeners. Compiler diagnostics use CompilerListener callbacks. Plugin contexts can publish their own notifications, such as the CPU context events used by SSEM's snapshot writer. VirtualComputer · EmulationController · Compiler

Plugin lookup and direct calls. A plugin registers a context instance under an interface. The pool verifies the instance implements that interface and checks the caller's connection to the provider at lookup. A TOML edge authorizes a lookup from from to to. bidirectional also permits the reverse lookup. The host's reserved ID 0 can look up any registered context. Once resolved, the caller holds a Java reference and calls it directly. The pool is outside subsequent memory reads, writes, and device calls. Unenforced conventions

Some expectations are documented in emuLib. The gaps below identify where runtime behavior still depends on the application, configuration author, or plugin honoring those expectations.

1. Publish contexts before consumers bind

Application and configuration. The host constructs all instances before initialize(), installs the topology, and uses a fixed order by role. It expects a CPU plugin to expose a CPUContext for host execution, even if peers use a more specific interface. The configuration must grant each consumer access to the intended provider.

Plugins. emuLib documents registration during construction and lookup in initialize(). Registration checks type, and lookup checks connectivity when it happens. The loader has no dependency declaration to verify early registration, required connections, or provider identity. A no-index lookup chooses the first accessible instance registered under that interface. An explicit index counts all entries under that interface. The typed helpers check the selected context's cell or data class after selection, so another accessible entry with the expected class can go unused.

Observed in BrainDuck. Brainc requests MemoryContext<Byte>, the CPU requests ByteMemoryContext, and VT100 requests BrainCPUContext to attach itself as the CPU's device. The configured edges and matching interfaces make those calls reach the intended objects. A valid edge alone cannot verify that the compiler and CPU use the same memory instance.

2. Hand off a runnable image and entry point

Application. The host calls compile(input, Optional.empty()) and counts ERROR diagnostics while that call is active. It assumes a return without an exception or error means the image is ready. It neither receives a typed compile result nor inspects the generated file before starting the CPU. The host parses -p as an integer and passes it to CPU reset without checking the machine's address range or alignment.

Plugins. The compiler must complete its image writes, entry-point update, and diagnostics before returning. The CPU must interpret the location in the compiler's address units and boot from the same memory. Brainc writes a HEX file, sets the shared program location, and loads memory when available. It emits a warning when memory is unavailable. A machine can therefore pass the compile error gate with an artifact on disk and no new image in the CPU's memory. A late diagnostic can also miss the gate. Compilation gate · Compiler contract · Brainc image load

3. Preserve the state needed for boot

Application. The host performs one full reset at load and a CPU-only reset just before the run. An omitted source relies on memory already being bootable after the first reset. CPU-only reset after compilation preserves the compiled image if the CPU honors that scope.

Plugins. Memory must restore any configured boot image at the right phase. Devices must preserve or refill staged inputs across the initial reset. VT100 consumes the headless input file during initialize(). Its reset resets the display and leaves the keyboard queue intact. Clearing that queue on the initial reset would remove input before the CPU reads it. The lifecycle has no readiness check for boot images or staged input. Reset and compile order · VT100 initialization and reset · VT100 input queue

4. Supply headless I/O and finish output

Application. EMUSTUDIO_AUTO describes automation mode. EMUSTUDIO_NO_GUI describes window availability. The host avoids opening device windows in headless mode and supplies a null GUI service. The launch path never checks isAutomationSupported(). It has no per-machine validation of required devices, file paths, or whether the run can proceed without user input. --input-file goes to the compiler. Guest input is configured on the device.

Plugins. Each plugin chooses how to honor the flags and when output is ready. BrainDuck's VT100 uses inputFileName and outputFileName in headless mode. Its file reader logs a missing input file, and a later CPU read waits on the queue. The reader provides no EOF marker. The display logs file open and write failures, so an apparently successful guest run can produce missing or incomplete output. With EMUSTUDIO_AUTO, the SSEM CPU observes its own context's stop notifications and writes a register and memory snapshot to ssem.out. RAM's abstract tape starts symbol logging during reset when both automation and headless mode are enabled.

5. Return from the worker when interrupted

Application. --waitmax bounds the wait for the running CPU's result. Configuration, initialization, reset, compilation, and device-window setup all precede that wait. On expiry, automation samples the state and proceeds toward close. Close interrupts active execution and waits for it to return before destroying plugins. There is no teardown deadline.

Plugins. The CPU API requires synchronous execution and prescribes STATE_RUNNING for a cooperative return after interruption without another terminal reason. The controller then resolves the requested stop or pause. Devices reached by the CPU worker must let interruption propagate through blocking I/O, and plugins must release their resources in destroy(). For example, VT100 restores the interrupt flag if its input queue wait is interrupted, so BrainDuck's loop can exit. A CPU loop or device call that ignores the interrupt can hold close indefinitely despite --waitmax. CPU.execute contract · Stop and close · Interruptible input · BrainDuck execution loop

6. Interpret success with context

Application. Automation returns failure for compilation errors, execution exceptions, address fallout, and bad instructions. A normal stop, breakpoint, or an elapsed wait with the CPU still running can all return exit code 0. A missing CPU skips execution. A missing compiler skips compilation even when the supplied source path exists. Plugin destruction errors are logged by VirtualComputer and can leave the exit status unchanged.

Plugins and callers. CPUs must return a faithful stop reason. Plugins must surface failures that should invalidate the run. Scripts that require a completed workload also need to verify its stop reason and expected output. The CLI currently has no single result containing phase, termination reason, and artifact status. What emuStudio needs to own

One application-owned session should decide when the machine starts, which windows open, whether operator input is allowed, and when the result is final. Plugins implement the machine's behavior and contribute views, prompts, device input and output, and artifacts through interfaces the application controls.

Widget factories leave window ownership with plugins

ApplicationApi.getGUI() returns either the host's Swing widget factory or null. The GUI interface returns Swing objects such as JPanel and JButton. It cannot schedule, veto, or close top-level windows created by plugin code. Device.showGUI(JFrame) and Plugin.showSettings(JFrame) explicitly let plugins show their own windows. VT100 uses the factory to build content and still creates, shows, and disposes its own terminal dialog. Memory erase actions even call JOptionPane directly for errors.

The audio tape player can call showGUI(null) from initialize() when showGuiAtStartup is set. That happens before the automation runner reaches its device-window phase. The flag prevents the bundled plugin from doing so in headless mode because the plugin reads it. The loader has no enforcement for another plugin that ignores the flag.

Change. Let plugins contribute content and request presentation by role, such as primary device view or settings. Let emuStudio create and own the window, resolve parenting, bring it forward, route close events, and dispose it. Supply the Swing GUI factory only when constructing desktop content on the event dispatch thread (EDT). Keep guest display and keyboard models usable when the host chooses to attach no desktop view.

Dialogs already defines the operator interface

AutomationCommand supplies DialogsGui with Swing or DialogsNoGui with a null GUI. DialogsNoGui logs messages, returns CANCEL for confirmation, and returns empty values for text, numbers, files, and directories. It never reads a terminal. Callers can receive the same empty value for user cancellation, invalid input, or prompts unavailable in their mode. A plugin that treats cancellation as an ordinary choice can continue with no operator ever seeing the request.

Change. Keep Dialogs as the host-provided interface for information, errors, confirmation, typed input, and path selection. Provide a terminal implementation that prompts on an attached terminal, parses answers, and requests paths as text. Let users explicitly allow operator interaction during automation. Use the same policy for machine selection. An interactive terminal can offer a list of computers, while batch mode requires an explicit selection. Report a required unanswered batch prompt as a run failure. Define how the interface conveys cancellation, invalid input, EOF, and interaction denied. Keep prompt text and diagnostics off any stream designated for machine output.

Keep guest I/O distinct. A plugin asking which tape to mount is an operator prompt. Characters a guest reads from a VT100 or pixels it writes to a display are machine traffic. The host can attach a window, terminal stream, file, or no backend to a device's supported I/O. If operator and guest input share a terminal, give one host-owned reader control and route bytes to the active recipient. Define guest EOF and terminal cancellation explicitly.

Device startup, cancellation, and completion need one owner

Startup gap. In headless automation, the tape player's reset() creates its AutomationController. Stored tape events start from the plugin's showGUI(). The host skips that hook with --no-gui, so the configured sequence never starts on this path. The plugin reports isAutomationSupported() == true. Calling showGUI() in a headless run would make device execution depend on a presentation callback.

Cancellation gap. The CPU worker and stop command already belong to EmulationController. In GUI automation, Automation enables Stop before showing device windows and calling start(). A Stop request in that interval can move the paused CPU to STATE_STOPPED_NORMAL and cause the subsequent start to fail with “Reset CPU first”. The progress dialog ignores the Stop future. In headless automation, the command supplies no operator control that translates terminal cancellation into the same stop request.

Completion gap. The host waits for CPU execution to return. Devices still own their own background work, and artifact production has no completion result. The SSEM CPU publishes its context state and writes ssem.out in a callback driven by those plugin events. On a cooperative interrupt, SSEM's context reports a breakpoint while the host can resolve the same return as a normal stop. The two streams answer different questions, so the plugin's state cannot serve as the run result.

Change. Give the session a single start, cancel, and finish path for desktop and terminal callers. Start configured device work through a machine lifecycle hook independent of view creation. The host controls when the hook runs relative to reset and the first instruction. A device can arm work before the CPU starts and advance using guest cycles after start. Give each worker a session lifetime, with cooperative cancel and acknowledged completion. Publish the host's final run reason once, collect requested device outputs after execution quiesces, and surface artifact and cleanup failures.

Choose the policy once, then supply the interfaces

The application can choose presentation, permission to prompt, and device I/O when it creates a session. Plugins request operations through the supplied interfaces. The host uses its mode flags to select implementations and grants only the capabilities available to each plugin. A windowed run can be unattended. A no-window run can be interactive. Audio, files, and console streams need their own policy. For example, the optional ZX Spectrum AY device opens host audio during initialization without testing EMUSTUDIO_NO_GUI for that operation. Replace the unconsulted isAutomationSupported() boolean with declared requirements the host can validate before execution. Check context bindings, device backends, operator availability, and output destinations for the selected machine. Give plugins the configured I/O and artifact destinations so the host can tell whether requested output was produced. Dispatch window operations on the EDT and keep it free to process Stop and close. Resolve prompts that block a machine operation before the operation where possible. If interactive prompts can occur during execution, route them through the session with cancellation and avoid making the EDT and machine worker wait for each other.

Enforce the interface at the level required

Bundled plugins. Permit Swing content construction in desktop view code. Require all plugin code to route top-level windows, prompts, and terminal reads through the host. Check module dependencies and call sites in the build. Use contract tests with a host that denies presentation, responds to prompts, records device startup, and requests cancellation. Run assembled-machine smoke tests in a no-display process with scripted input and a separate terminal-interaction test. Verify outcomes and artifacts, including headless tape events, VT100 EOF, and SSEM snapshots.

Runtime enforcement. The application can enforce policy for operations that reach its interfaces. The current loader runs plugin JARs in the host JVM, where arbitrary plugin code can reach Swing and other JDK APIs directly. Capability declarations, build checks, and a headless JVM are useful for supported plugins. If emuStudio needs to enforce a hard run deadline against uncooperative code, the host needs a worker process it can terminate. Restricting what untrusted plugins can access also requires OS controls for display, terminal, and host resources. Process isolation changes the direct-reference context model, so treat it as a separate architectural decision. Current plugin loader

Review priorities

  1. Separate device lifecycle from presentation. Give the host an explicit device startup hook and independent window ownership. Prove a configured tape sequence starts in both windowed and headless automation, and that early cancellation never becomes a startup error.
  2. Put operator interaction behind Dialogs. Add terminal and batch policies. Exercise the same plugin prompt through Swing, a terminal, and unattended execution. Check that guest I/O and result streams stay distinct from operator traffic.
  3. Make readiness and outcomes explicit. Verify the program image, target memory, entry point, device capabilities, and I/O configuration. Report termination, deadline expiry, artifacts, and cleanup separately in the run result. Test a CPU blocked in guest I/O and a CPU that ignores interruption.
